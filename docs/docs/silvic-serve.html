silvic-serve

Scores LightGBM models, model.txt from LightGBM 3.3.5 or 4.x or from silvic, with LightGBM’s predictions bit for bit. A 3,000-row batch through 2,000 trees of 53 leaves takes 12.2 ms on one Apple M4 Pro core, against 64.0 ms for lleaves 1.1.0 and 581.6 ms for LightGBM. Python reaches it as silvic.serve, in the silvic package.

import silvic.serve

predictor = silvic.serve.Predictor("model.txt")
scores = predictor.predict(candidates, num_threads=1)

model = silvic.serve.Model(model_file="model.txt")  # where lleaves.Model was
model.compile()
scores = model.predict(candidates, n_jobs=1)

Public API

silvic.serve.Predictor(model, kernel=None)
Compiles a silvic.Booster, a lightgbm.Booster, model text or a model file, in milliseconds.
predictor.predict(data, raw_score=False, num_iteration=None, num_threads=1)
One score per row of numpy (f32 or f64, C or Fortran order) or pandas, with categories mapped as at training. One thread scores on the calling thread, 0 on every core. Releases the GIL.
silvic.serve.Model(model_file=None, model_str=None)
lleaves’ Model: compile() records raw_score and ignores lleaves’ tuning options, and predict(data, n_jobs=None) uses every core unless told otherwise, as lleaves does.
Predictor::new(&model), predictor.predict(&rows, raw_score, num_trees, num_threads)
The same from Rust, on a silvic_core::Model and a DenseMatrix; predict_raw writes raw scores into a caller’s buffer.
Kernel, Predictor::with_kernel(&model, kernel), available_kernels()
neon, avx2, avx512 or portable. Kernel::detect picks NEON on aarch64 and AVX2 on x86-64 that has it, else the portable kernel.

Also public predictor.kernel, predictor.num_trees(), predictor.num_feature(), Predictor::num_walked_trees.

How it scores

Each tree is QuickScorer’s leaf bitvector (Lucchese et al., SIGIR 2015): leaves are numbered left to right, each node clears its left subtree’s bits in the rows that go right, and the lowest bit left is the exit leaf, so no branch depends on the data. Rows are scored 64 at a time, one SIMD byte lane per row, with each tree’s bitvectors sliced into bytes across the lanes, as in RapidScorer (Ye et al., KDD 2018). Before that, each value becomes a byte: its rank among the split thresholds of its feature, found by a branchless binary search over all lanes at once, so every split is a byte compare. Leaf values are added per row in tree order, in f64, as LightGBM adds them.

NaN and zero take the codes left or right of every threshold that LightGBM’s missing-value handling and default_left send them to, and values within kZeroThreshold of zero read as zero, as in LightGBM’s dense reader. Categories that every split treats alike share a class, and a categorical split is a 64-byte table; NaN, negative and unseen categories go right.

Trees of more than 256 leaves, a NaN threshold, or a categorical feature with more than 64 distinct category behaviours are walked node by node with silvic-core’s decisions instead: every model silvic-core reads scores, those trees at LightGBM’s speed.

Kernels

neon aarch64
64 rows per block. Timed above.
avx2 x86-64
64 rows per block. Its tests pass under Rosetta 2; its speed on x86 is not yet measured.
avx512
Compiles but has not run on AVX-512 hardware, so it is used only when asked for by name.
portable
Plain Rust, eight byte lanes to a u64 word, 32 rows per block: 37.5 ms for the batch above.

Every kernel gives the same predictions, tested bit for bit against LightGBM 3.3.5 and 4.7’s own predictions and against silvic-core on random forests, at every threshold and its neighbouring doubles, NaN, ±0, ±kZeroThreshold and ±inf.
